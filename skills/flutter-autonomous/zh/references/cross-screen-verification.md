# 跨屏验证——证明一屏看不出来的性质

`dump ui` 返回的是**视口**，不是列表。所以凡是正确性跨越"一屏装不下"的性质——分页顺序、跨页不重复、"到底了没有"、时间线的分组头——**单次 dump 判不了，肉眼更判不了**：出问题的地方通常在几百条以下，没人会手动滚到那儿。

解法的形状永远一样：**逐屏采集 → 拼成一条全局序列 → 用代码在序列上断言**。

## 什么时候用

任何会分页、会流式追加、会分组的列表：交易历史、聊天记录、信息流、搜索结果、排行榜、日志页、无限表格。识别标志是需求在说**整个列表**——"按时间排序""不重复""翻页正常""能到底"——而屏幕只给你一个窗口。

一屏装得下就别搞这套：dump 一次直接断言。

## 方法

### 1. 采集——每滚一屏 dump 一次，**落盘**

```bash
D=<deviceId>
for i in $(seq 1 40); do
  mobilecli io swipe --device $D 540,1700,540,500 >/dev/null 2>&1
  sleep 1.8                                    # 等列表停稳，也等这一页加载完
  mobilecli dump ui --device $D > /tmp/scan_$i.json
done
```

滚动距离**必须小于一个视口**，让相邻两次 dump 有重叠——拼接靠的就是这段重叠来对齐。一次 fling 跳三屏会静默漏掉中间的条目，而你根本不会知道漏了什么。

### 2. 拼接——用重叠去重，保持顺序

按轮次顺序走，每轮内部按 `rect.y` 排序，没见过的条目就追加。相邻轮的重叠会自动塌掉，得到的就是列表从上到下的真实样子。

### 3. 判定——三条机器可判的判据

| 判据 | 怎么判 | 为什么必须是这个形式 |
|---|---|---|
| **无真重复** | 某条目出现的轮次集合**不连续**（第 3 轮出现过，第 9 轮又出现） | 相邻轮重复只是视口重叠，**本来就该重复**。只有隔了一段又冒出来，才说明列表里真的有两份。直接数重复次数的话，每一条都会误报 |
| **顺序单调** | 走一遍拼好的序列，标出方向不对的相邻对 | 分页 bug 就住在这儿——通常只在尾部，两个数据源在不同深度耗尽的地方 |
| **分组头唯一且有序** | 收集日期/分节头，查重复与方向 | 同一个分组头出现两次 = 同一组数据被两页各吐了一遍 |

报**违例条数** + 头几个违例连同它的前后邻居。"0 逆序 / 0 重复"是能拿来做决定的结论，"看着挺顺"不是。

## 可复用骨架

写成文件按前缀调用——你会跑很多遍，每次内联重写就是转写错误的来源。

```python
# /tmp/analyze.py <prefix>   → 读 /tmp/<prefix>_*.json
import json, re, sys, glob
from collections import defaultdict

PAT = re.compile(r'<条目可能的全部文案变体>')      # 见坑 1
files = sorted(glob.glob(f'/tmp/{sys.argv[1]}_*.json'),
               key=lambda f: int(re.search(r'_(\d+)\.json', f).group(1)))

rounds = {}
for f in files:
    idx = int(re.search(r'_(\d+)\.json', f).group(1))
    items = []
    def walk(o):                      # dump 是嵌套树，递归找，别假设层级
        if isinstance(o, dict):
            label, rect = o.get('label'), o.get('rect') or {}
            if isinstance(label, str) and PAT.search(label) and <排除顶栏/筛选 chip>:
                items.append((rect.get('y', 0), label))
            for v in o.values(): walk(v)
        elif isinstance(o, list):
            for v in o: walk(v)
    walk(json.load(open(f)))
    items.sort()                                    # 屏内从上到下
    rounds[idx] = [l for _, l in items]

occ = defaultdict(list)                             # 条目 -> 出现过的轮次
for i, ls in rounds.items():
    for l in ls: occ[l].append(i)

seq, seen = [], set()                               # 拼好的全局序列
for i in sorted(rounds):
    for l in rounds[i]:
        if l not in seen: seen.add(l); seq.append(l)

gaps = {k: v for k, v in occ.items() if max(v) - min(v) + 1 != len(set(v))}
print(f"唯一={len(occ)} 真重复={len(gaps)}")
# 然后从每条 label 里解析出有序字段，检查相邻对
```

**保留按轮次的数据（`rounds`），不要只留拍平的序列**——轮次下标正是"真重复"这条判据能成立的前提。

## 三个坑，一个坑一轮时间

### 1. 先校准尺子；结论看着不对时，先怀疑尺子

**写过滤条件之前，先 dump 一屏把 label 的全部形态读一遍。**一个渲染"买入 / 卖出"的列表，多半也渲染"转入 / 转出 / 返佣 / 退款"，而漏掉一个变体的过滤器不只是漏几行——如果分组头是合并进该组第一条的（通常都是），**它会把分组头一起漏掉**，后面每一条的归组就全错位了。

一条干净的列表就是这样产出**两处看起来无懈可击的顺序违例**的。数据没问题，是尺子短了。

> **规则：结论说"异常"时，先验证判定方法，再去查被测对象。**假信号当成真的去追，追得越认真代价越大。

便宜的校准手段：`唯一条目数` 应与 `采到的总行数` 在同一量级差几个百分点；截图里能看到的每个分组头，都该出现在你的分组头列表里。数字看着别扭，就是过滤器写错了。

### 2. "画面不动"有三种意思

| 你看到的 | 真实原因 | 怎么区分 |
|---|---|---|
| 前后 dump 一致 | 手势压根没送达 | 换**另一条通道**发同样的 swipe（`adb shell input swipe` ↔ `mobilecli io swipe`），另一条能动就说明第一条被吞了 |
| 前后 dump 一致 | **列表本来就到底了**——Android 默认 ClampingScrollPhysics 没有 overscroll，到底后 fling **零位移**、零滚动通知 | 读列表末尾的状态标识（见下）；到底后 fling 本就是空操作，不是故障 |
| 前后 dump 一致 | 真卡住了（某次加载永远不完成） | 排除上面两种之后才能下这个结论 |

三种在 `dump ui` 里**逐字节一样**，所以必须有这套判别流程——否则你会对着一条已经结束的列表无限重试手势，或者对着一条其实挂住的列表宣布"已到底"。

拍板靠的是状态标识，于是引出：

> **"列不出来 = 回去改代码"的推论：区分不出来的状态，同样是代码缺陷。**一个 footer 用无文字的转圈表示"加载中"、用 `SizedBox.shrink()` 表示"静止"，在语义树里**是同一个"什么都没有"**。给每个状态挂稳定的 `Semantics(identifier:)`（`paging_footer_loading` / `_nomore` / `_fail`），一次 dump 就有答案。没有它，你只能截图猜、再加临时日志热重载跑一遍——本该一次往返的事变成三次。

### 3. 原始数据别进上下文

40 轮扫描就是 40 份几十 KB 的 dump。**绝不要把它们读进上下文。**dump 落盘，判定下沉到 shell（`jq` / `python`），只把结论读回来——几行字。`logcat` 同理：用 `grep`/`sed` 在管道里过滤，不要用眼睛过滤。

截图是单次最贵的（每张约 1500–2500 token），而且**不可机器判定**——只有当判断确实需要"人眼看"（转圈的视觉状态、布局、颜色）时才拍。判断"数据对不对"，走 dump + 脚本这条路又便宜又可靠。

这么做，100 屏的扫描只花很少上下文，可以长时间连续跑；反过来每份 dump 都整个读进来，一趟就能把窗口撑爆。

## 成本控制：能跳就别滚

靠滑动把列表推到底是这套流程里最贵的一环：每屏约 2.5 秒、100+ 屏，而且往往要跑好几趟（修复前取证、修复后、最终回归）。一趟就是几分钟，且每次 swipe 都是一次工具往返。

**如果被测性质住在列表深处，就给被测对象加一个 debug-only 的一步到位入口**——debug 面板里一个按钮驱动分页控制器直到耗尽，或者一个 VM Service `evaluate` 钩子。验证于是变成：跳到底 → dump → 断言。跟主文档（§元素驱动交互）里 deeplink 抄近路是同一个道理，只是这次抄的是**状态深度**而不是导航深度，而且通常是能拿到的最大一笔收益。
